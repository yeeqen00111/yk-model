# yk-model 架构蓝图（v0.1）

> 使命：让 AI 模型在**普通笔记本**上跑得动、跑得快、装得上。
> 定位：不是追赶云侧性能，而是把"笔记本 = 小型异构集群"当作一等公民来设计。
> 本文件是项目锚点：所有后续代码、实验、决策都从这里长出来，改动它先改这里的理由。

---

## 0. 一句话路线

**三元/低比特权重的现实底座（bitnet.cpp / T-MAC / llama.cpp 骨架）之上，自研"拓扑感知 + 冷热分级驻留 + 熵路由"的运行时调度层。复用没有设计意义的标准件，自研承载设计逻辑的控制面。**

一句反话明确边界：**我们不从零写矩阵乘，也从零写调度。**

## 1. 物理约束（先于一切）

### 1.1 铁律：解码瓶颈是内存带宽，不是算力

- 证据：H100 上单 token 数学运算 < 0.1ms，实际 30ms/token，卡在带宽；2012–2022 算力增长 ~80×，带宽仅 ~17×（"内存墙"）；decode 占推理耗时 90%+。
- 推论：吞吐 ≈ 内存带宽 / 量化后模型大小。**所有设计决策的第一判据是"每 token 要跨内存搬运多少字节、搬多快"。**

### 1.2 目标拓扑矩阵（四级，默认只有一块设备，甚至只有 CPU）

| 档 | 拓扑 | 带宽/容量画像 | 执行策略 |
|---|---|---|---|
| T0 | CPU + 核显（无独显） | DDR 单/双通道 25–90 GB/s，iGPU 共享内存 | 三元/低比特全驻留，CPU 位运算 + AVX-512，iGPU 可选辅助 |
| T1 | 核显 + 大内存（32GB+） | 共享带宽、容量大 | 三元 MoE / 更大模型全驻留 |
| T2 | 独显 4–8GB + 系统内存 | VRAM 200–256 GB/s，容量小 | 73V双重常驻 + 冷层回落 CPU |
| T3 | 8–16GB 显存 / Apple 统一内存 | 大显存 | 显存定档，再考虑并载 |
| T4 | 带 NPU（Core Ultra / Snapdragon X / Ryzen AI） | NPU 低功耗 | 轻任务/prefill 分流；绝不视为必需 |

> 设计前提（反写）：**默认只有一块可用设备，甚至只有 CPU；多设备是增量，不是先决。**

## 2. 本机（开发/验收环境）画像

**T0 档，最低配目标机，也是最苛刻的验收机。**

| 项 | 实测值 | 影响 |
|---|---|---|
| CPU | i7-1165G7（Tiger Lake）4C/8T，支持 **AVX-512 VNNI** | 三元/查表内核的本命指令集，bitnet.cpp/T-MAC 能吃到 |
| 核显 | Iris Xe（96EU） | 共享内存，缓存只受限系统内存 |
| 内存 | **16GB 单条 DDR4-3200（单通道）** | 短板：~25.6 GB/s；加一条内存 → 双通道 ~51 GB/s，吞吐近翻倍 |
| 独显/NPU | 无 | T0 拓扑；T2/T3 路径无法在本机开发，需云 GPU 验证 |
| 磁盘 | C: 余 16GB，D: 余 142GB | 工具链/模型全装 D: |

### 本机能力边界（诚实预估）
- 7B Q4（~4.4GB）：单通道顶格 ~5 tok/s，能跑但慢。
- 3B Q4（~1.9GB）：~12 tok/s，可用舒适区。
- **BitNet 1.58-2B4T（0.4GB）**：内存成本近零，走 AVX-512 位运算，预期 30–48 tok/s —— **本机甜点路线**。
- 训练：**本机不做。** 预训练/QAT 上云（8/24GB GPU 实例即可）；本机最多 ≤1B 的 LoRA 概念验证。

## 3. 证据地图（检索结论，已核验）

| 主张 | 证据 | 状态 |
|---|---|---|
| 解码=带宽瓶颈 | 内存墙、decode>90% 时间 | ✅ 成立 |
| 三元权重改写内存账本 | BitNet b1.58-2B4T 全模型 0.4GB、29ms/token；x86 提速 2.37–6.17×、能耗降 ~82% | ✅ 成立 |
| 低比特+稀疏治 MoE 带宽病 | MoQE：仅专家 2-bit，不退训，体积 -79.6%，专家层更耐低比特；MH-MoE：1-bit 下 MoE 仍有效 | ✅ 成立 |
| 引擎重写=查表/位并行而非反量化 | T-MAC：LUT mpGEMM，比 llama.cpp 吞吐高 4×、能耗降 70%；Surface AI PC 上 3B BitNet 48 tok/s | ✅ 成立 |
| 三元+MoE 将成方向 | 社区已有同类论题，Qwen3 30B/3B 激活为前兆 | 🔶 开放前沿 |

关键来源：
- bitnet.cpp（微软，github.com/microsoft/bitnet）—— 骨架基于 llama.cpp，内核基于 T-MAC
- BitNet a4.8《4-bit Activations for 1-bit LLMs》—— 4-bit 激活 + 仅激活 55% 参数 + 3-bit KV
- MoQE《Mixture of Quantized Experts》—— 专家层超低比特量化
- T-MAC《CPU Renaissance via Table Lookup for Low-Bit LLM》—— LUT 查表 mpGEMM

## 4. 设计原则（三条主张）

1. **权重经济决定一切**：从训练起就为低比特生（1.58-bit 三值 / 2-bit MoE 专家），而不是事后量化。存储与带宽同源优化。
2. **跨层权重搬运只在"切换粒度"，绝不在 decode 粒度**：热权重（主导解码的 FFN/attention）常驻对应内存层；系统内存只存低频可热拔的冷权重（如 MoE 冷专家）。这直接否定"每 token 每层重读"的 offload 老路。
3. **按难度分配算力（熵路由）**：廉价工件（低比特稀疏子网/推测草稿）出候选，难的交给大头。在带宽受限的本机上，这是数量级差距。

## 5. 分层架构（复用 vs 自研的切割）

| 层 | 内容 | 策略 |
|---|---|---|
| **内核/算子层** | 查表内积、AVX-512 位运算、mpGEMM | **复用** T-MAC / bitnet.cpp 内核 |
| **引擎骨架层** | tokenizer、GGUF 加载、采样、KV 管理、多后端抽象 | **复用** llama.cpp 骨架（与微软同款起手） |
| **运行时/调度层** ⭐ | 拓扑感知、冷热分级驻留、熵路由、多设备编排、分级内存管理 | **自研** —— 本项目核心增量，现有框架均无 |

### 自研层的具体模块（roadmap 内拆解）
- **DrawShell**（拓扑探测）：不查 PCI 清单猜，跑微型基准实测每设备真实可用带宽/可用性 → 输出机器 Profile。
- **ResidencyManager**（冷热分级驻留）：按 Profile 设置驻留边界与搬运粒度；T0 几乎无搬运，T2 的墙在"独显 VS 内存"。
- **Scheduler**（熵路由/推测解码）：难度感知的 cheap-first 解码路径。
- **Profile 自动级配**：按探测结果自动选执行路径、模型部署档（若多档发布）、内存分层策略。

## 6. 模型侧路线

- 底座选 **BitNet 系 / 可训生态**（1.58-bit 三值权重），配 a4.8 式稀疏化（4-bit 激活 + 部分激活 + 3-bit KV）。
- 目标形态：**细粒度混合级配** —— 专家权重 2-bit、共享参数 8-bit，一份权重多档部署（T0/T2 各自档位自动选择）。
- 训练：**云上**。分布：部分用现成开源 small-ternary 模型起步，验证路线后再考虑自训练。

---

## 7. 风险与护栏

1. **BitNet 小模型掉点**（MH-MoE 实证：规模小时 1-bit 退化）→ 1–3B 档保留 Q4 稠密退路。
2. **MoE+1bit 的路由负载均衡/专家热迁移**是开放问题 → 先单专家架构跑通，再上 MoE。
3. **iGPU+dGPU 异构**在笔记本上非坦途（MUX 关核显、PCIe 同步开销）→ 降级为可选优化，不做主线。
4. 单通道内存是本机硬伤 → 建议加内存双通道（最大单项增益）。

| 阶段 | 内容 | 验收标准 |

## 9. 开发语言与环境（裁定向：本机不装任何 C/C++ 工具链）

### 9.1 语言分工
- **自研控制面（核心增量）= Python 3.11（conda 管理）**：拓扑探测、冷热驻留策略、熵路由、自动级配、基准脚本——全是决策逻辑，无内核算子，Python 足够快、零编译、零占空间。
- **复用的计算面 = 预编译 C++ 引擎**：用 llama.cpp 官方 Windows 预编译发布（win-avx512，吃本机 AVX-512）或 llama-cpp-python wheel，**只调引擎、不装编译器**。

### 9.2 C++ 工具链：推迟且轻量化
- 触发器：**仅当**需要把驻留/调度逻辑嵌进引擎内部 decode 循环（P2+）时再装。
- 届时用轻量替代，不碰 MSVC（10GB+）：**Zig**（自带 clang，下载 ~50MB）或 **WinLibs MinGW-w64**（~1GB，装 D:）。

### 9.3 存储纪律
- 代码 / conda / 模型 / 下载全部 `D:\`（142GB 可用）；C:（仅 16GB）**不装任何工具链**。
- **Python 环境 = conda（Miniconda 已在 `D:\application\env\miniconda3`，天然在 D:）**。本项目用独立 env：`conda create -n yk-model python=3.11`（envs 落在 conda 自身 D: 目录下，不与 hermes 的 venv 混用）。
