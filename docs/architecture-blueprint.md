# yk-model 架构蓝图（v0.1）

> 使命：让 AI 模型在**普通笔记本**上跑得动、跑得快、装得上。
> 定位：不是追赶云侧性能，而是把"笔记本 = 小型异构集群"当作一等公民来设计。
> 本文件是项目锚点：所有后续代码、实验、决策都从这里长出来，改动它先改这里的理由。

---

## 0. 一句话路线

**引擎全自研 + 模型全自研：在普通笔记本上，从训练到推理全链路自成一个系统——三元/低比特模型自训，推理引擎（内存管理、算子、调度、KV、tokenizer）全部自写。不依赖任何现成推理框架（如 llama.cpp / bitnet.cpp / T-MAC）作为运行时底座。**

兼容的边界：参考而不依赖现成框架；论文/算法可参考，代码不带走别人的实现主体（见 §5 自研边界）。

> 路线历史：曾先为"分层复用 + 自研调度"（v0.1），2026-09-20 由用户决策改为"引擎全自研 + 模型全自研"，见第 11 节决策日志。

## 1. 物理约束（先于一切）

### 1.1 铁律：解码瓶颈是内存带宽，不是算力

- 证据：H100 上单 token 数学运算 < 0.1ms，实际 30ms/token，卡在带宽；2012–2022 算力增长 ~80×，带宽仅 ~17×（"内存墙"）；decode 占推理耗时 90%+。
- 推论：吞吐 ≈ 内存带宽 / 量化后模型大小。**所有设计决策的第一判据是"每 token 要跨内存搬运多少字节、搬多快"。**

### 1.2 目标拓扑矩阵（五级，默认只有一块设备，甚至只有 CPU）

| 档 | 拓扑 | 带宽/容量画像 | 执行策略 |
|---|---|---|---|
| T0 | CPU + 核显（无独显） | DDR 单/双通道 25–90 GB/s，iGPU 共享内存 | 三元/低比特全驻留，CPU 位运算 + AVX-512，iGPU 可选辅助 |
| T1 | 核显 + 大内存（32GB+） | 共享带宽、容量大 | 三元 MoE / 更大模型全驻留 |
| T2 | 独显 4–8GB + 系统内存 | VRAM 200–256 GB/s，容量小 | 低比特常驻 VRAM + 冷层回落 CPU |
| T3 | 8–16GB 显存 / Apple 统一内存 | 大显存 | 显存定档，再考虑并载 |
| T4 | 带 NPU（Core Ultra / Snapdragon X / Ryzen AI） | NPU 低功耗 | 轻任务/prefill 分流；绝不视为必需 |

> 设计前提（反写）：**默认只有一块可用设备，甚至只有 CPU；多设备是增量，不是先决。**

## 2. 本机（开发/验收环境）画像

**T0 档，最低配目标机，也是最苛刻的验收机。**

| 项 | 实测值 | 影响 |
|---|---|---|
| CPU | i7-1165G7（Tiger Lake）4C/8T，支持 **AVX-512 VNNI** | 三元/查表内核的本命指令集，自研内核实现优先吃满它 |
| 核显 | Iris Xe（96EU） | 共享内存，缓存只受限系统内存 |
| 内存 | **16GB 单条 DDR4-3200（单通道）** | 短板：~25.6 GB/s；加一条内存 → 双通道 ~51 GB/s，吞吐近翻倍 |
| 独显/NPU | 无 | T0 拓扑；T2/T3 路径无法在本机开发，需云 GPU 验证 |
| 磁盘 | C: 余 16GB，D: 余 142GB | 工具链/模型全装 D: |

### 本机能力边界（诚实预估）
- 7B Q4（~4.4GB）：单通道顶格 ~5 tok/s，能跑但慢。
- 3B Q4（~1.9GB）：~12 tok/s，可用舒适区。
- **1.58-bit 三元量级（参照：BitNet 2B-4T 全模型 0.4GB，本机预期 30–48 tok/s）**：这条带宽账量级上是本机甜点区间，我们的自训模型按此档设计（§6.4 Gen-0 0.4–0.7B）。
- 训练：**本机不做。** 预训练/QAT 上云（8/24GB GPU 实例即可）；本机最多 ≤1B 的 LoRA 概念验证。

## 3. 证据地图（检索结论，已核验）

| 主张 | 证据 | 状态 |
|---|---|---|
| 解码=带宽瓶颈 | 内存墙、decode>90% 时间 | ✅ 成立 |
| 三元权重改写内存账本 | BitNet b1.58-2B4T 全模型 0.4GB、29ms/token；x86 提速 2.37–6.17×、能耗降 ~82% | ✅ 成立 |
| 低比特+稀疏治 MoE 带宽病 | MoQE：仅专家 2-bit，不退训，体积 -79.6%，专家层更耐低比特；MH-MoE：1-bit 下 MoE 仍有效 | ✅ 成立 |
| 引擎重写=查表/位并行而非反量化 | T-MAC：LUT mpGEMM，比 llama.cpp 吞吐高 4×、能耗降 70%；Surface AI PC 上 3B BitNet 48 tok/s | ✅ 成立 |
| 三元+MoE 将成方向 | 社区已有同类论题，Qwen3 30B/3B 激活为前兆 | 🔶 开放前沿 |

关键来源：
- bitnet.cpp（微软，github.com/microsoft/bitnet）—— 骨架基于 llama.cpp，内核基于 T-MAC
- BitNet a4.8《4-bit Activations for 1-bit LLMs》—— 4-bit 激活 + 仅激活 55% 参数 + 3-bit KV
- MoQE《Mixture of Quantized Experts》—— 专家层超低比特量化
- T-MAC《CPU Renaissance via Table Lookup for Low-Bit LLM》—— LUT 查表 mpGEMM

## 4. 设计原则（三条主张）

1. **权重经济决定一切**：从训练起就为低比特生（1.58-bit 三值 / 2-bit MoE 专家），而不是事后量化。存储与带宽同源优化。
2. **跨层权重搬运只在"切换粒度"，绝不在 decode 粒度**：热权重（主导解码的 FFN/attention）常驻对应内存层；系统内存只存低频可热拔的冷权重（如 MoE 冷专家）。这直接否定"每 token 每层重读"的 offload 老路。
3. **按难度分配算力（熵路由）**：廉价工件（低比特稀疏子网/推测草稿）出候选，难的交给大头。在带宽受限的本机上，这是数量级差距。

## 5. 分层架构（全自研边界：参考算法，不抄实现）

| 层 | 内容 | 策略 |
|---|---|---|
| **内核/算子层** | 查表内积、AVX-512 位运算、mpGEMM、量化格式 | **自研**（论文算法可参考：T-MAC LUT、BitNet 三值化等，代码自写） |
| **模型层** | tokenizer、加载格式、KV 管理 | **自研**（tokenizer 自建 / 或自研 BPE，不依赖第三方运行库） |
| **运行时/调度层** ⭐ | 拓扑感知、冷热分级驻留、熵路由、多设备编排、分级内存管理 | **自研** |

> 原则：**不带走任何现成框架的实现主体**（llama.cpp / bitnet.cpp / T-MAC 代码不并入）；论文/公开算法的"思想"可参考，所有代码、数据结构、格式、内核由本项目自写。

### 自研层的具体模块（roadmap 内拆解）
- **DrawShell**（拓扑探测）：不查 PCI 清单猜，跑微型基准实测每设备真实可用带宽/可用性 → 输出机器 Profile。
- **ResidencyManager**（冷热分级驻留）：按 Profile 设置驻留边界与搬运粒度；T0 几乎无搬运，T2 的墙在"独显 VS 内存"。
- **Scheduler**（熵路由/推测解码）：难度感知的 cheap-first 解码路径。
- **Profile 自动级配**：按探测结果自动选执行路径、模型部署档（若多档发布）、内存分层策略。
- **格式/加载器**：自研模型权重格式与加载（对齐范围依设计定）。

## 6. 模型侧路线：YkNet（全自研架构）

### 6.1 一句话定义
> **YkNet = 切片级三元 MoE（slice-level ternary MoE） + 逐 token 动态深度（熵路由下沉到架构层） + 细粒度冷热切片驻留（冷切片落盘） + 分级精度（8-bit 关键层 / 三元 FFN 主干）。**
> 主心骨：把"每 token 要流的字节数"和"资源驻留的粒度"两件事同时推到现役方案没占的位置——针对 25.6GB/s 带宽墙与"内存 16G / 盘 142G"不对称结构设计。

### 6.2 四件套的动机
1. **分级精度**：注意力/关键层给 8-bit，FFN 主干三元（1.58-bit）。对冲小模型低比特退化（MH-MoE 实证）。
2. **切片级三元 MoE**：FFN 拆成 K 个 low-rank 切片（三元权重块 + 微型路由头），token 只激活 top-k 片。对比整只专家 MoE：
   - 负载均衡更天然（细粒度路由），不需要重 aux loss 训练才稳（同 DeepSeekMoE 思路）；
   - 驻留粒度最细——"切片"就是冷热驻留/迁移的天然最小单位。
3. **动态深度（熵路由下沉）**：token 按难度决定计算量——简单 token 只过部分切片，难的走全宽 FFN。让"按难度分配算力"成为架构默认行为而非外壳。
4. **冷切片落盘**：利用 16G 内存 vs 142G 盘的暗桶——不常用冷专家切片迁到 D: 盘，热切片常驻内存。带宽劣一个量级但冷切片每 token 只读零点几字节 → 容量上限从"内存"推到"磁盘"，与 ResidencyManager 自然对接。

### 6.3 与现役方案的位置对比（对 T0 机器）

| 方案 | 每 token 激活字节 | 容量上限 | 驻留粒度 | 短板 |
|---|---|---|---|---|
| BitNet 稠密三元 | 全量（最差） | 内存内 | — | 带宽吃死、KV 压力 |
| a4.8 稀疏激活 | 全量×0.55 | 内存内 | — | 只省 45% |
| 整只专家 MoE | top-k 专家 | 内存内 | 粗 | 负载均衡难、驻留粒度粗 |
| **YkNet v0** | **top-k 切片×0.3–0.6** | **盘+内存叠加** | **切片（细）** | 训练/路由复杂度高 |

### 6.4 落地路线（分代）
- **Gen-0（立闭环）**：Dense 三元 0.4–0.7B + 分级精度。跑通「训练→格式→引擎→推理」全链路并测基线。地基。
- **Gen-1（真增量）**：切片级三元 MoE（~5B 总参 / ~1B 激活）+ 动态深度 + 冷热切片驻留（冷落盘）。YkNet 完整形态。
- **Gen-2**：MoE 放大 + 上下文策略强化（RAG + 短窗口 + KV 量化）。
- 风险对冲：切片路由若跑不稳 → 退回 Gen-0 形态，两方向都能继续，不烂尾。

### 6.5 训练
- 全云上（8/24GB GPU 实例起步）；QAT 从训练起（STE 直通估计），借鉴 a4.8 两阶段法（8-bit 激活收敛后再切 4-bit）。
- 训练框架作为工具使用（PyTorch 类通用库），不侵入运行时；权重为自产。
- 备注：冷落盘收益随总规模增大才显著，Gen-1（~5B 总量级）的收益有限；它朝 20B+ 增长，是"架构朝着这个目标长"而非 Gen-1 吃满。

### 6.6 基座与知识策略（不需要通用基座，用户决策 2026-09-20）

- **不造大型通用基座**：全自研 + 单卡训练 + 本机小模型三重约束下，自建"通用大基座"成本与质量双重不可行。
- **模型 = 能力（推理/读写/结构化/按指令做事），不装世界知识**；知识全部外挂。
- **知识 = 本地文档库/检索外挂（RAG 策略）**，与蓝图既定上下文策略（RAG + 短窗口）自洽闭合。
- 定位：**专用 + 私密 + 快**，优势不在通用而在垂直能力与本地私库。
- 后续形态：先窄通用/专用能力端到端训练，通用度靠外挂补齐；若未来扩大通用度，需重谈云上算力/语料/时间预算。

## 6A. 推理引擎架构（YkEngine）

> 引擎不是另一个独立发明——它从上节的 YkNet 长出来。本节先立契约，再给结构。

### 6A.1 YkNet → YkEngine 接口契约（模型对引擎的硬性要求）

| # | 契约 | 必需性 | 由 YkNet 哪一点驱动 |
|---|---|---|---|
| C1 | **逐 token 动态执行**：每个 token 的执行路径可按模型决策改变（激活哪些切片、走多深），不得按静态图一次性固定 | 必需 | 切片路由 + 动态深度 |
| C2 | **切片级寻址与计量**：权重文件最小可寻址/可装卸单位是"切片"（mmap 页、迁移、热度统计的最小单元） | 必需 | 切片级 MoE + 冷热驻留 |
| C3 | **分级精度解码**：同一模型内含多种精度张量（8-bit 关键层 / 三元 FFN），内核按元数据选解码方式 | 必需 | 分级精度 |
| C4 | **熵/难度信号通道**：模型内部决策所需的不确定性信号要能快速回传，供动态深度分支使用 | 必需 | 动态深度 |
| C5 | **KV 量化**：KV 层支持 Q8（默认），预留 Q4/3-bit 预案 | 建议 | a4.8 式 KV 量化 |
| C6 | **批量能力**：支持 batch>1 以吃满 CPU GEMM 并行（v0 可单请求优先，接口预留） | 建议 | 带宽-bound 下的并行利用 |

> 契约 = "引擎=基于模型架构"的严格含义。不满足上述任一必需要求的设计不算合格的 YkEngine。

### 6A.2 引擎分层结构（C/C++ 自研）

```
YkEngine
├── kern   内核层      三元乘(LUT/VNNI)·分级精度GEMM(int8/int4)·softmax(量化域)
│                     ·KV量化·路由(top-k/熵/分数排序)·embedding/unembedding
├── exec   执行器      per-token决策执行(模型给激活切片清单+深度选择)
│                     ·三阶段流水：决策→预取→执行 ·线程池(4C/8T) ·批次管理(batch>1备用)
├── mem    内存/驻留层  mmap权重文件打底 ·热区(常驻RAM:热切片+共享层8bit)
│                     ·冷区(RAM按需换入/page cache) ·切片粒度迁移+热度统计(LFU)
│                     ·显式预取提示(路由决策→prefetch冷切片近层)
├── kv     KV管理层    环形短窗口KV(默认4K) ·Q8打包与量化内核 ·窗口滑动重置
└── ctx    上下文层    对话 ·采样(top-k/top-p/温度/种子) ·logits后处理 ·前缀缓存(RAG复用)
```

### 6A.3 逐 token 三阶段执行流水（决策 → 预取 → 执行）

对每个 token：
1. **决策**：极小 GEMM 读路由/熵 → 得出"激活切片集合 + 深度选择" → 生成预取清单；
2. **预取**：将清单中的冷切片写到 page cache / 热区（与上一步并行衔接）；
3. **执行**：只执行激活路径（top-k 切片 + 共享关键层）。

→ 这是"每 token 只读需要读的字节"的落地机制，也直接服务带宽铁律。

### 6A.4 YkFormat 权重格式（v0 草案）

```
YkFormat 单文件
├── header         magic "YKF0" · 版本 · 系列/层数/上下文/精度策略
├── TensorTable   每张量的 名称/形状/精度/偏移/长度
├── SliceTable    每个切片的 (张量段,偏移,长度,驻留层hint,热度初值) ← C2 的最小寻址表
└── data          三元2bit打包 · 8bit块 · KV量化scale表 · 页对齐(4096)支持mmap直读
```

- 页对齐保证冷切片"整页存取"，mmap 下命中即用、冷区即换。
- SliceTable 是 mem 层驻留/迁移可直接索引的元数据，与 C2 一一对应。

### 6A.5 暂定实现细节（留给对应阶段实测，不预锁）

- 线程模型细节（硬核/超线程是否开启、token 内并行切分）→ P0/P1 实测带宽决定
- 路由在权重内的编排形态（多级路由等）→ Gen-1 训练决定
- 前缀缓存结构 / KV 窗口具体值锁定 → P2 定

## 7. 风险与护栏

1. **小模型低比特退化**（MH-MoE 实证）→ 分级精度对冲 + Gen-0 先验证，必要时保留 Q4 稠密退路。
2. **切片路由训练稳定性**是 YkNet 最大不确定点 → 小规模（≤1B）先实测；跑不动即退回 Gen-0 形态。
3. **冷落盘收益随总规模增大才显著** → 明确它为"朝 20B+ 长"的长期项，Gen-1 不过度依赖。
4. **MoE 路由负载均衡** → 细粒度切片天然均衡，仍需监控；先小规模验证。
5. **iGPU+dGPU 异构**在笔记本上非坦途（MUX 关核显、PCIe 同步开销）→ 降级为可选优化，不做主线。
6. 单通道内存是本机硬伤 → 建议加内存双通道（最大单项增益）。

|---|---|---|

## 9. 开发语言与环境（裁定向：本机不装任何 C/C++ 工具链）

### 9.1 语言分工（全自研版）
- **引擎主体 = C/C++（自研）**：矩阵乘、tokenizer、加载、KV、调度。本机即需可编译环境。
- **控制面/基准/训练脚本 = Python 3.11（项目 env `yk-model`）**：DrawShell 探测、驻留策略、熵路由的编排逻辑、基准与数据解析。

### 9.2 C++ 工具链：轻量化（不碰 MSVC，用户明示）
- 用 **Zig**（自带 clang，下载 ~50MB）或 **WinLibs MinGW-w64**（~1GB）作为 C/C++ 工具链，装 D:；**不装 MSVC（10GB+）**。

## 10. 装配与分发（全自研版：无第三方运行时依赖）

### 10.1 仓库结构（git，轻，只放自研源码）
```
yk-model/                    ← git 仓库
├── engine/   自研引擎源码(C/C++)          （P0 起逐步填充）
├── train/    自研训练脚本                 （Gen-0 起填充）
├── docs/     文档
├── dist/     yk-release.yaml 清单 + yk 安装器（自研）   ← 获取入口
└── ...
```
- D:\build 编译产物、D:\model-store 大文件（引擎二进制/模型权重）**不入库**。

### 10.2 分发三件套（与行业标准一致，不发明新玩具）
1. **模型权重（GB 级，自训）** → 上传 **ModelScope/HuggingFace**（默认双源，图内可换源）。仓库只存 `model_id + sha256`。
2. **引擎二进制（自研编译产物）** → 发 **Gitee/GitHub Release**（同 llama.cpp 同逻辑）。源码在仓库，可自build。
3. **`yk install`（自研 CLI）**：clone 仓库 → 一条命令 → 按 `yk-release.yaml` 自动拉取模型（魔搭/HF）+ 引擎（Release），核验 SHA256，归位到 `D:\model-store`。首次使用多跑一条命令，换取仓库永远轻量。
   - 初期（开发期）：模型先放本地 `D:\model-store\models\`，`yk install` 先走本地 stub，后续再补上传动作（用户决策 2026-09-20）。
   - `yk on` 常用场景有 `install / run / list` 等子命令（后续在 P0 细化）。

### 10.3 yk-release.yaml 字段（草案）
```yaml
schema: yk-release/v1
version: 0.0.1
engine:
  source: gitee|github   # 发布源
  tag: v0.0.1
  sha256: <引擎二进制sha256>
models:
  - id: <model_id>           # 魔搭/HF 上的 ID
    sha256: <权重sha256>
    local: D:/model-store/models/gen0/  # 本地暂存路径（开发期）
```

### 10.4 基准/复现
- 仓库 + `yk install` ⇒ 复现任何版本：源码可自 build，二进制经 SHA 校验，可追溯到发布 tag。

- ⚠️ 遗留物记录：P0 早期误下载的 `D:\model-store\engines\llama.cpp\`（llama.cpp b11060 二进制）已**不属本项目**，未并入代码/清单；是否清理由用户定。
